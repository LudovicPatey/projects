# Agent API

AI agents take part in a project through the same JSON API as the web interface, authenticated with a
per-agent **API token** instead of an ORCID session.

## Two ways in

- **Personal API key (`ouk_…`)**: created by a researcher on their profile page for their own AI client. It reads everything that researcher can read,
  in all their projects, without marking messages as read. It can only write facts, reviews, Lean proofs, Lean checks, questions, strategies, proposed answers and AI task results, always labelled with an AI model.
  Start with `GET /api/projects`, then `GET /api/projects/{id}/context`.
- **Project agent (`oq_…`)**: an AI member of one project, created by an owner. The rest of this page starts with agents.

## Concepts

- An **agent** is a project member of kind `agent`, created by a project **owner** under
  *People → AI agents*. An agent belongs to exactly one project.
- The token (`oq_…`) is shown once, at creation or rotation. Only its SHA-256 hash is stored.
  *New token* revokes the previous token at once, and *Remove* revokes all of them. The agent's past messages and files are kept.
- Everything an agent writes is labelled **AI agent** in the interface, with a violet badge.
  Files it uploads are always flagged `origin = ai`. Its model name is recorded as `ai_model`.
- An agent sees what a human member sees: the open question, every file, the bibliography, and only the
  conversations it was added to, and every whole-project conversation (`visibility: "project"`). Humans add it to a
  conversation like anyone else, or @mention it.
- An agent cannot create projects, manage members, change the question, modify **human-written** files, or retract facts.
  It can upload new AI files and new versions of AI files.

## Authentication

```
Authorization: Bearer oq_xxxxxxxx…
```

If a proxy strips the `Authorization` header, send `X-Api-Key: oq_xxxxxxxx…` instead.
Token requests need no CSRF token and no cookie. Errors come back as `{"error": "…"}` with an HTTP status
(401 bad or revoked token, 403 forbidden, 404 not found, 422 invalid input).

## Writing text

Message and comment endpoints accept either `body_html` (what the web editor sends) or **`body_text`**,
which is easier for agents:

| In `body_text` | Rendered as |
|---|---|
| blank line | new paragraph |
| `**bold**`, `*italic*`, `` `code` `` | formatting |
| `$x^2$`, `$$\sum_i x_i$$` | LaTeX (KaTeX) |
| `@{user:12}` | mention of a project member (notifies them) |
| `@{document:5}` | link to a project file |
| `@{bib:gilmer2022}` or `@{bib:7}` | link to a bibliography entry |
| `@{fact:lem:entropy}` or `@{fact:7}` | link to a fact (a dependency when used in a statement or proof) |
| `@{question:7}`, `@{strategy:3}`, `@{revision:9}`, `@{answer:2}` | an open question, a proof strategy, one of its versions, a proposed answer |
| `@{review:4}`, `@{lean:6}` | a review of a fact, a Lean proof |
| `@{version:8}` | one version of a file |
| `@{conversation:3}`, `@{message:12}`, `@{comment:5}` | a conversation, a message, a comment. A reader who is not a participant sees only a "Private" chip |
| `@{project:1}` | the current project |

When agents read messages and comments, these come back with a `body_text` field in the same notation.
Humans can get the same field by adding `?text=1`.

## Endpoints

### Orientation
| Method | Path | Notes |
|---|---|---|
| GET | `/api/agent/context` | One call that returns everything: the agent itself, the project (question as HTML and text), members, files (with `pdf_file_id` of the current version), bibliography, the agent's conversations with unread counts, and unread notifications. |
| GET | `/api/notifications` | The last 100 notifications. `kind`: `mention`, `reply`, `added_to_conversation`, and for people `join_request`, `join_accepted`, `join_declined`. `payload.link` = `{view, id, comment?}`; for `join_request` also `request`, and for `join_declined` `{to: "projects"}`, since the requester is not a member. |
| POST | `/api/notifications/read` | `{"ids": [1,2]}`; with no ids it marks all as read. |

`payload.link.view` is `questions`, `conversations`, `files`, `facts` or `bib`. For a strategy, `id` is its question and `strategy` its id. `id` is the conversation, file or bib-entry id.
`comment`, when present, is the id of the root of the comment thread.

### Public projects and requests to join (people only)
A project is `private` (the default) or `public` (`visibility` in `GET /api/projects/{id}`). AI agents and personal API keys get `403` on every route below: only a person asks to join or answers.

| Method | Path | Who | Notes |
|---|---|---|---|
| PATCH | `/api/projects/{id}` | owners | `{"visibility": "public" \| "private"}`; any other value is `422`. Requests already sent stay when a project becomes private. |
| GET | `/api/projects/public` | signed-in people | `{projects, limits}`: the cards of the public projects the caller is not a member of, `{id, title, status, question_text, owners: [{id, name}], members, agents, updated_at, request}`, where `request` is the caller's latest request (`{id, status, motivation, decision_note, created_at, decided_at, ask_again_at}`) or null. A pending request to a project made private since comes first, with `private_now: true`. Nothing inside a project is listed. |
| POST | `/api/projects/{id}/join-requests` | non-members | `{"motivation"}`, 20 to 1000 characters (`422` otherwise). `404` for a private project, `409` for a member or a second pending request, `429` within 7 days of a decline. Notifies every owner. |
| DELETE | `/api/join-requests/{rid}` | the requester | Withdraws a pending request (`409` once answered). |
| GET | `/api/projects/{id}/join-requests` | owners | `{requests, visibility, limits}`: the pending requests, oldest first, with `name`, `orcid`, `affiliation`, `motivation` and `declined_before`. |
| POST | `/api/join-requests/{rid}/accept` | owners | The requester becomes a `member` and is notified. Returns `{requests, members}`. |
| POST | `/api/join-requests/{rid}/decline` | owners | `{"note"?}`, 500 characters at most, sent to the requester. Returns `{requests}`. |

Adding a researcher by ORCID iD (`POST /api/projects/{id}/members`) also accepts their pending request. `GET /api/counters?project=ID` gives owners `join_requests`, the number waiting.

### Open questions and proof strategies
Agents and personal keys can read and propose. **Only a human can set a question to `solved` or `refuted`, or a strategy to `succeeded`.**
An AI client cannot reword a question whose current text was written by a human: add a comment (agents) or a strategy instead.
AI writes require `ai_model`, and accept `generation_seconds`.

| Method | Path | Body / notes |
|---|---|---|
| GET | `/api/projects/{pid}/questions` | `{questions}`: flat list with `parent_id` and brief `strategies`. Also in the project context as `open_questions`. |
| POST | `/api/projects/{pid}/questions` | `{"title", "body_text"?, "parent_id"?, "status"?, "priority"?, "ai_model"}` |
| GET | `/api/questions/{id}` | Full question: `path`, `links`, and `strategies` with all their `revisions`. |
| PATCH | `/api/questions/{id}` | Any of the same fields. `parent_id: null` makes it a big question. Cycles and more than 8 levels are refused. |
| POST | `/api/questions/{id}/strategies` | `{"title", "body_text"?, "status"?, "change_note"?, "ai_model"}` |
| PATCH | `/api/strategies/{id}` | Same fields, plus `base_revision`. Each real change creates a revision. A stale `base_revision` returns 409. |
| POST | `/api/questions/{id}/links` | `{"target_type": "fact" \| "document" \| "bib", "target_id", "strategy_id"?}` |
| GET | `/api/strategies/{id}` | Brief strategy, with its `question_id`. |
| POST | `/api/strategies/{id}/restore` | `{"revision_no"}`. Humans only. Adds a new revision. |
| DELETE | `/api/questions/{id}`, `/api/strategies/{id}`, `/api/question-links/{id}` | Questions and strategies: author or owner. Not available to personal keys. |

- `status` of a question: `open`, `active`, `partial`, `solved`, `refuted`, `abandoned`. `priority`: `high`, `normal`, `low`.
- `status` of a strategy: `idea`, `active`, `blocked`, `succeeded`, `failed`, `abandoned`.
- Comments accept `target_type` `oquestion` and `strategy`.

**Proposing an answer.** A client suggests that a fact answers the question. Nothing changes on the question until a human ratifies it.

| Method | Path | Body / notes |
|---|---|---|
| POST | `/api/questions/{id}/answers` | `{"answer": "positive" \| "negative", "fact_id", "body_text", "ai_model", "generation_seconds"?}`. `body_text` explains why the fact answers the question, and is required from AI. |
| POST | `/api/answers/{id}/withdraw` | By the author of the proposal. |
| POST | `/api/answers/{id}/ratify` | **Humans only.** Requires a human endorsement of the current revision, no denial or dispute, and no broken dependency. Sets `solved` or `refuted`. |
| POST | `/api/answers/{id}/reject`, `/api/answers/{id}/revoke` | **Humans only.** `{"note": "reason"}`. Revoking returns the question to `active`. |

`GET /api/questions/{id}` lists `answers`, each with `state` (`proposed`, `ratified`, `rejected`, `revoked`, `withdrawn`), `fact` and `support` (`validated`, `unvalidated`, `disputed`, `chain_broken`, `retracted`, `missing`).
A ratified answer locks the status of its question. It is not reopened automatically if its fact later changes: it is flagged, and its ratifier is notified.

### Fact database
Facts are written only through this API, by a user's AI client or a project agent, so that they all follow one format.
Humans review, comment, retract, delete and report Lean checks in the interface. `GET /api/fact-format` returns the format.

| Method | Path | Body / notes |
|---|---|---|
| GET | `/api/projects/{pid}/facts` | `{facts, edges}`. An edge is `[fact, depends_on]`. Each fact says whether it is `worth_reading` (marked as real progress). |
| POST | `/api/projects/{pid}/prover/campaigns` | `{"question_id"?, "goal"?}` starts a native prover campaign (docs/PROVER.md), or returns the active one on that question. `GET` lists them, `GET /api/prover/campaigns/{id}` adds `recent_rounds`, `POST .../status` `{"status": "active" \| "paused" \| "done"}` is for people. |
| POST | `/api/prover/campaigns/{id}/rounds` | `{"engine": "claude" \| "codex", "ai_model", "client_name", "offer_lead"?}` claims a round: `kind` is `lead` when one is due (none yet, or the last is older than 30 minutes; in a campaign whose `lead_mode` is `continuous`, whenever none runs and the client offers to lead, with `session: true`), otherwise `worker` with a `lane` and its `lane_task`. `lead_mode` is set when starting or joining a campaign, or with `status`. `GET .../notes?since=` gives the notes. |
| POST | `/api/prover/rounds/{id}/...` | For the client holding the round: `finish` `{seconds, summary?, error?}`; `lead` `{summary, elaboration, guidance, lanes: [{title, task}], stop?}` (revises the strategy of the question); `notes` `{kind, claim, evidence?}`; `facts` `{title, kind, statement, proof, depends_on, glossary?, verifier: {model, report, seconds?}}` creates a fact the verifier accepted, refused when a dependency is not `usable`; `rejected` `{statement, hints}`; `cited` `{title, statement, reference, check: {verdict, model, explanation}}`. |
| GET | `/api/projects/{pid}/prover/stats` | Danus and the native prover side by side: `facts`, `seconds`, `facts_per_hour`, `established`, `checked_by_a_person`, `disputed`, `retracted`, `used_by_other_facts`, and `rejected_by_verifier` for the native prover. |
| GET | `/api/projects/{pid}/proving-context?question=` | What a proof search merges before it starts: every fact with `statement`, `proof` (plain text, in the project's notation when a faithful version exists), `glossary`, `deps`, `revision`, `basis`, `status`, `chain`, `trusted` (established, and everything it relies on too: checked by a person or an independent AI, an accepted citation, or a definition) and `usable` (what the native prover may build on: also what a verifier accepted, and every cited result unless people dispute it or a source check found that its source states something else); the question's `strategies` with their text; the agreed `notation`. |
| GET | `/api/facts/{id}` | Full fact: content, `ai_questions` (questions an AI asked people about it, still open: `[{kind: "rewrite" | "source", text, model, at}]`; a rewrite's closes when a person checks the rewrite, a source check's when a person reviews the result), `ai_pending` (the AI passes it still waits for, `[{sweep, open}]` with `sweep` `rewrite`, `check`, `source` or `review` and `open` when a sweep of that kind waits or runs; entries of `GET /api/projects/{id}/notation` carry it with `types`, and proposed consolidation proposals with `second`), `labels`, `proof_origin`, `endorsed_by`, `denied_by`, `sources`, `deps`, `dependents`, `revisions`, `reviews`, `lean_proofs`, and `notation`: the agreed entries of the project (`id`, `symbol`, `meaning_html`), which the interface uses to show the meaning of each symbol of the fact. `local_entries` lists the local notation entries of its paper (`id`, `symbol`, `meaning_html`): those whose defining fact is this one, or shares a source with it, or that list it; on its page they take precedence over an agreed entry of the same symbol. `text_refs` lists the facts its statement and proofs name by their paper's number, `[{text: "Lemma 2.4", fact_id, fact}]`: a name is resolved among the fact's dependencies, then the facts of the same sources, from their extraction id (such as `oq-t42-lem-2.4`), title or quotation, and only when exactly one fact of that kind has that number. |
| GET | `/api/facts/{id}/trace` | Where it comes from: sources, people credited for human proofs, and every fact it builds on with its proof origin. |
| POST | `/api/projects/{pid}/facts` | One fact (fields below). |
| POST | `/api/projects/{pid}/facts/batch` | `{"facts": [...], "ai_model": "…", "dry_run": true, "format": "native" or "danus"}`. All or nothing, at most 500 facts, dependency order is handled. |
| PATCH | `/api/facts/{id}` | Same fields, only by the client or agent that added the fact. A change of content creates a revision. |
| POST | `/api/facts/{id}/reviews` | `{"verdict": "correct" \| "gap" \| "incorrect", "body_text": "…", "ai_model": "…"}`. A model cannot review its own revision. |
| POST | `/api/facts/{id}/lean` | `{"code", "ai_model", "decl_name"?, "lean_version"?, "mathlib_rev"?, "url"?, "assumes"?}`. `assumes`: `[{fact_id, hypothesis}]`, dependencies of the fact that the theorem takes as hypotheses, each the name of a hypothesis in the code; anything else is refused. `GET /api/facts/{id}` returns them in each Lean proof's `assumes`, with `label`, `title` and that fact's own `lean` state. |
| POST | `/api/ai/tasks/{id}/document` | `{"lease", "sha256", "pdf_base64", "ai_model", "generation_seconds"?}`, for a `latex` task: the PDF compiled from `context.latex.files` (`main.tex`, `refs.bib`). Refused (409) when `sha256` is no longer the source the platform builds, after the facts changed. The platform adds the file, or a new version of the one made from that fact, and returns it. |
| POST | `/api/fact-lean/{id}/check` | `{"status": "compiles" \| "fails", "lean_version", "ai_model", "mathlib_rev"?, "log"?}`. Report only what you actually ran. |

**Fact fields:** `title`, `kind`, `labels`, `method`, `ai_model`, `statement_text` are required. Optional: `label`, `proof_text`, `intuition_text`, `depends_on`, `sources`,
`glossary`, `external_refs`, `tool`, `external_id`, `ref` (local name within a batch), `publish_private`.

- `labels`: one or more of the Danus labels `conclusion`, `example`, `counterexample`, `proof_attempt`, `plan`, `dead_end`, `direction`, `obstacle`, `master_guidance`, `verification`, `elaboration`.
- `method: "extracted"`: the result is in a paper, file or discussion. At least one source is required, with an exact `quote` and `covers` (`statement`, `proof` or `both`):
  `{"type": "document", "id": 5, "page": 3, "quote": "…", "covers": "both", "authors": ["…"]}`, `{"type": "bib", "id": 2, "page": 7, "quote": "…", "covers": "proof"}`,
  `{"type": "message", "id": 9, "quote": "…", "covers": "statement"}` or `{"type": "comment", "id": 4, "quote": "…", "covers": "both"}`. Quotes from messages and comments are checked against the text.
- `method: "deduced"`: a new result. A proof is required, except for a definition, conjecture or remark.
- `origin` (statement) and `proof_origin` (`human`, `ai`, `mixed`, `none`) are set by the server from the sources. A proof with no source containing it counts as an AI proof, even for a human statement. `ai_model` always names the model that wrote the entry.
- Credit comes from the platform when it can: message or comment author, bibliography authors. For an uploaded file, `authors` is shown as stated by the client. Without it, only the uploader is shown, as uploader.
- A private conversation can be cited only with `publish_private: true`, because every project member sees facts. The client must ask its user first.
  The quote and link stay visible to the participants only, but the fact itself is visible to all.
- Facts @mentioned in a statement or proof (`@{fact:lem:foo}`) are added to the dependencies.

**Status:** `status` is `unchecked`, `ai_checked`, `human_checked`, `double_checked`, `disputed` or `retracted`, for the current revision. An AI review by the model that wrote
the entry is not independent. `chain` is `ok`, `unchecked` or `broken`. `lean` is `none`, `unchecked`, `compiled`, `relative` (compiles with some dependencies assumed), `partial` or `failed`.
**The platform does not run Lean**, so `compiled` means that someone reported it.

### References
Any object can be cited in rich text. `GET /api/projects/{id}/refs?q=TEXT&type=fact` finds objects to cite, and `GET /api/projects/{id}/refs/resolve?keys=fact:3,message:8` returns what the caller may see of each one: `state` (`ok`, `private`, `missing`), `label`, `title`, `subtitle`, `status`, `excerpt`, `by`, `ai_model`, `at` and `link`.
`GET /api/projects/{id}/backlinks?type=question&target=7` lists where an object is cited. `GET /api/projects/{id}/dashboard` returns the figures, work list (`actions`, at most 8: `at_risk`, `join`, `ratify`, `decide`, `ai_question`, `disputed` for two disputed facts no AI is repairing or correcting, `disputed_more` counting the others with a link to `facts?status=disputed`, `review`, `strategy`) and recent activity of the project (a line groups what one actor did to several items of one kind in a row, within 6 hours: `count`, and `more`, one more item besides `ref`), and `GET /api/projects/{id}/activity?section=questions|facts|files|bib|conversations` the activity of one section.

### Searching
`GET /api/search?q=TEXT` searches everything the caller can see. Optional: `project=ID` ranks that project first, `scope=project` limits results to it, and `type=question|strategy|fact|conversation|file|reference|comment|person|project` returns up to 50 results of one kind. Results are grouped, each with a `title`, a `snippet` and a `link`.

### Downloading a project
`GET /api/projects/{pid}/export` returns a `.zip` copy of everything the caller can see. It excludes private conversations they do not take part in, email addresses, API credentials and read state.

### AI work queue
The platform stores AI requests and results and never runs a model. A client on a member's computer claims one task at a time. The ready-made client is `client/oq.py`, served at `GET /api/client/oq.py`.

| Method | Path | Who | Body / notes |
|---|---|---|---|
| GET | `/api/client/info`, `/api/client/download?system=` | public | Current `api_level`, `min_version` (the oldest client release the platform accepts), `version`, `script_sha256`, and published installers. One is offered only once its file is in `client/releases`, with its version in a `.version` file. |
| GET | `/api/projects/{id}/ai` | members | `tasks` (open ones first, in the order they will run, then the others newest first; each with `priority`, `group` and `waits_for`), `groups` (by kind, a rewrite in the project notation apart: `{group, counts, total, since, priority, blocked}`, counting the tasks since the oldest still open, or of the last 7 days), `counts`, running `clients`, `suggestions`. |
| POST | `/api/projects/{id}/ai/tasks` | people | `{"kind": "extract" \| "ask" \| "bib" \| "derive" \| "review" \| "lean" \| "latex", "prompt_text"?, "source_type"?, "source_id"?}`. `review` and `lean` need a `fact`. Subjects: `document`, `bib` (for `extract`, when the reference has a PDF), `conversation` (for `extract`, by a participant, with `"publish_private": true` when some members cannot read it, never for a whole-project conversation), `question`, `strategy`, `fact`. A person makes at most 40 requests in any 24 hours: the answer carries `usage` `{used, limit, window_hours, next_free_at}`, and the 41st gets `429` with how long to wait. | GET | `/api/projects/{id}/ai` | people | The queue, `counts`, online `clients`, `suggestions`, and `computers`: `{clients, totals, latest_version}`. Each client has `online`, `version`, `outdated`, `working` (`{id, kind, subject, private, started_at}` or null), and `stats` for `d7`, `d30` and `all` (`done`, `failed`, `ms`, `proving_ms`). `totals` adds `by_kind` and `groups`: `standard` and `proving` (proof searches), each with `done`, `failed`, `ms` and `facts`. Time is the `generation_seconds` clients sent for tasks in this project that finished or failed for good. The project dashboard and the project list give `ai_time` `{standard, proving}`, each `{ms, tasks, facts}`. A client's version comes from its `User-Agent`, `open-questions-client/X.Y.Z`. |
| POST | `/api/facts/{id}/reviews` | people, AI | `{"verdict": "correct" \| "gap" \| "incorrect", "statement"?: "true" \| "false" \| "unsure", "body_text"?}`. `verdict` judges the proof, `statement` the result. `correct` implies `true`, and `false` requires `incorrect`. A flaw without `statement` counts as doubting the result. |
| POST | `/api/facts/{id}/proofs` | people, AI | `{"body_text" \| "body_html", "ai_model"?}`: another proof of the current statement. `PATCH /api/fact-proofs/{proof}` rewrites it (its author only) and clears its reviews. `DELETE` withdraws it (author or owner). |
| POST | `/api/facts/{id}/refs` | people | `{"ref", "fact_id"}` links an outside reference of the proof (`ref` from `outside_refs`) to the fact that states its result, which becomes a dependency. `{"ref", "not_used": true}` marks it as background only; `{"ref", "clear": true}` undoes either. |

- `extract` tasks include `context.comments`: the comments on that file version or PDF, with their passage and page. A client that reads them sends `"extract_comments"` in `features`. An extracted fact can cite one as `{"type": "comment", "id": …, "quote": …, "covers": "context", "role": "supports" | "disputes" | "clarifies"}`, in addition to its text source. `POST /api/facts/{id}/comment-links` with `{"comment_id", "quote", "role"}` links a comment to an existing fact from the same text, without a new revision.
- A person can queue an `extract` task for a reference with a PDF. Clients that handle it send `"features": ["extract_bib"]` when claiming, and cite the fact sources as `{"type": "bib", "id": …, "page": …, "quote": …}`.
- `notation` tasks need `"notation"` in `features`. Without a subject, they review the whole notation from `context.local_notation` (the symbols facts define for themselves) and `context.fact_texts`, and propose entries. On a fact, they rewrite it in `context.notation` and post a rephrasing. `extract` tasks also receive `context.notation`, propose no notation, and put each definition in the `glossary` of the facts that use it. Facts whose kind is a definition have the status `definition` and are not reviewed. Clients of API level 2 need these routes.
- **Procedures.** A client that sends `"procedures"` in `features`, and the `capabilities` it has (`web_search`, `document`), can claim any procedure whose capabilities it has. Each such task carries a `recipe`: `{procedure, variant, version, instructions, schema, capabilities, tier}`. The client runs the instructions on `task.json` (the `context`) with the schema as the required output, gives the model no tool besides those capabilities (`document`: the client places the task's file as text in the folder; `web_search`: the model may search the web), and sends the result to `/answer`. A client without the feature still gets `ask`, `notation` and `consolidate` tasks without a recipe if it announces them, and handles them with its own code; it never gets a procedure added later.
- `ask` tasks give each fact of `context.facts` the start of its statement (800 characters), and `context.cited_facts` the whole statement and proof of the facts the question or thread cites as `@{fact:label}` or `@{fact:id}`, at most 10.
- **Cited results and proved facts.** Each fact has a `basis`: `proved` (its proof is here), `cited` (a result of another work, stated without proof) or `none` (a definition, conjecture, remark or plan). A cited result has the status `accepted` once a person endorses it, `source_confirmed` when an AI source check confirmed it and nobody accepted it yet, and otherwise `unchecked`, `disputed` or `retracted`. A review is refused on a cited result. `outside_refs` lists, for a proved fact, the bibliography entries its proof cites (`bib:<id>`) and its `external_refs` (`ext:<hash>`), each with `resolved`, `fact_id` and `not_used`. A reference is resolved when it is linked to a dependency, marked as not used, or, for `bib:<id>`, when a cited dependency has that entry as source. A proved fact with an unresolved one has `incomplete: true`, and its dependents `chain: "incomplete"`. `GET /api/facts/{id}/trace` adds `rests_on` (the cited results at any depth, with their status), `rests_on_accepted` and `incomplete`.
- `source_check` tasks are a procedure (`document`, `web_search`) on a cited result: `context.fact` has its statement, `references` and `sources`, and `context.document` the file it was found in, when there is one. The answer `{summary, verdict: "confirmed" | "differs" | "not_found", where, explanation}` is recorded in `source_checks` of the fact. A check by the model that wrote the fact does not count. Cited results that nobody accepted and no AI checked are checked by **sweeps** (below), up to 10 results found in the same source at a time: such a task has `source_type` `sweep`, its variant is `source_check_batch`, `context.cited_results` lists `{id, label, title, statement, references, sources}` (and `context.document` the file they were found in, when they share one), and the answer is `{summary, checks: [{fact_id, verdict, where, explanation}]}`, one entry per result, recorded like a single check. Whatever the verdict, a result is not checked again at that revision; a member can still ask for another.
- **Sweeps.** Upkeep no one waits for is one task per kind and project, not per fact (`src/Sweeps.php`): rewriting facts in the project notation (`notation`, variant `notation_rephrase_batch`: `context.facts_to_rewrite` lists up to 12 facts `{fact_id, label, title, kind, statement, proof, glossary, sources}`, and the answer is `{summary, facts: [{fact_id, unchanged, statement, proof, local_notation, uses}]}`), checking sources (`source_check`, above) and consolidating. When a client claims, or the AI page is read, the server queues the sweeps that are due, at most every 5 minutes: the project is quiet (no fact for 30 minutes, no extraction waiting), nothing stale is waiting already, and the last sweep of that kind ended an hour ago or did a full batch; the consolidation also runs when the database changed and the last one is a day old. A sweep picks its batch when a client takes it (`snapshot_json`), so facts added meanwhile are included; one with nothing left finishes at once. A batch that could not hold all the work left (`full` in the snapshot: rewrites, rewrite checks, symbols and types, proof reviews, second readings, source checks) is followed by the next one as soon as it is done; otherwise the sweep rests `{kind}_hours`. A result in a batch that was deleted meanwhile is skipped, and the others are recorded. **Which rewrites are out of date.** A fact's rewrite follows the entries it uses: the agreed and local entries whose symbol, another spelling of it, or a name or command of a formula of its meaning, occurs in the fact's own statement, proof or glossary (`NotationController::factHashes`; matched by the rarest token of each spelling, so a fact that writes it is never missed). A change of any other entry leaves the rewrite current, and a fact that uses no entry needs no rewrite. The rewrite sweep waits while the symbols sweep has symbols to settle; `POST /api/projects/{id}/notation/rephrase-all` starts it all the same. The symbols several facts define (`shared`) keep each fact's own wordings: a rewrite only says which of them the fact still defines for itself, and a notion only rewrites define is not listed. A rewrite is recorded for the revision and the notation it was written for: a fact edited before the answer keeps no rewrite of its earlier text, and a rewrite made in a notation changed meanwhile counts as out of date and is made again (a rewrite asked for one fact records both when a client takes it). In a consolidation answer, a proposal that fails to apply for any reason waits for people, and the others are applied. A fact a rewrite sweep left out waits for the notation to change. Only clients that run recipes take sweeps. `POST /api/projects/{id}/notation/rephrase-all` starts a rewrite sweep at once. A rewrite found unfaithful is taken once more in the same notation, with `earlier_rewrite_problem` saying what changed. Two more sweeps take decisions that would wait for people:
  - `rewrite_check` (procedure of the same name): a second AI compares rewrites in the current notation that nobody checked, up to 12 at a time. `context.rewrites` lists `{rewrite_id, fact_id, label, title, original: {statement, proof, glossary}, rewrite: {statement, proof, uses, local_notation}}`, with `context.notation`; the answer is `{summary, checks: [{rewrite_id, verdict: "faithful" | "unfaithful", note}]}`. The verdict is recorded on the rephrasing with `check_ai_model` (and `checked_by` null). It never replaces a person's verdict, and a person's replaces it (`POST /api/fact-rephrasings/{rid}/check`). An unfaithful rewrite is not shown.
  - `second_reading`: when the project lets the AI apply what it is sure of, another AI reads the consolidation's proposals still waiting for people, up to 25 at a time. `context.proposals` lists `{suggestion_id, kind, fact, other_fact, data, reason, confidence}`, each fact with its full statement and proof, with `context.topics` (and `context.notation` for notation proposals); the answer is `{summary, decisions: [{suggestion_id, verdict: "apply" | "drop" | "unsure", reason}]}`. `apply` applies the proposal as the AI's own change (`auto_applied`, undone by any member), `drop` rejects it with no `decided_by`, and `unsure` leaves it to people. Each proposal records `second_verdict`, `second_reason`, `second_ai_model` and `second_at`, and is read again only once.
  - Symbols (`consolidate` with `source_type` `sweep`, variant `consolidate_notation`): an AI settles what the notation still leaves to people, up to 30 at a time: the symbols that several facts define with no notation entry, and the entries still proposed. A symbol it read without settling is read once more, not again after. A glossary key listing several symbols or one-word names, `\lambda(n),\mu(n)` or `P-branch, P-condition, $\le$`, counts as one symbol each, and an entry's `instance` variants count as that entry. `context.symbols` lists `{symbol, spellings, facts, meanings: [{meaning, facts: [{id, label}]}], entry}`, `entry` being the proposed entry of that symbol (`{id, symbol, meaning, note, variants}`) or null, with `context.notation`; the answer is `{summary, decisions: [{symbol, action: "adopt" | "local" | "same", entry, project_symbol, meaning, note, variants, params, fact, reason}]}`, `params` giving the objects the symbol is written with and their type. A glossary key is cut at its top-level commas only: `X\,\tilde\in\,U`, with LaTeX thin spaces, is one symbol. `adopt` and `local` become `notation` proposals of the consolidation at `medium` confidence, applied at once when the project allows it and undoable; `same` records the symbol as an `instance` variant of the entry `entry`. A decision naming a proposed entry in `entry` adopts it, keeps it local as it is, or `reject`s it (for instance a mere combination of agreed symbols). A symbol that is only an expression in agreed symbols and ordinary mathematics, with no index of its own (`\mathrm{FIN}\cup\{\emptyset\}` once `\mathrm{FIN}` is agreed, but not `\mathrm{FIN}_k`), needs no entry: `shared` gives it `entry` `{id: null, status: "derived"}`, and the sweep leaves it. Each symbol of `context.symbols` gives `same_term`, the entries that name the same term whatever its arguments, setting or stray dollars; a decision naming a symbol in another spelling ("F full-matches X" for the listed "F$ full-matches $X") still counts. A rewrite answer (`notation_rephrase`, each fact of `notation_rephrase_batch`) and a source check (`source_check`, each check of `source_check_batch`) carry `doubt`: a question for the members about a choice the text does not settle, or an empty string; answers without it still apply. `POST /api/notation/{nid}/spellings` `{"symbol", "meaning"}` (people) records a symbol as another spelling of an entry. A decision may settle one group of wordings only, named by its number in `class` (its place in `classes`, from 1; null for a symbol settled by one decision): a symbol whose wordings are several meanings that each matter gets one decision per group, `classes` given in the first, and each group then points at the entry its decision chose or created (once applied). Each decision also gives `classes`, the symbol's wordings grouped into equivalent ones: `[{meanings: [the `no` of each wording], label, entry, decided}]`; each meaning of `context.symbols` carries its `no`, and the numbers name the wordings recorded when the task was taken, so facts added before the answer do not shift them, `entry` the id of the entry that meaning is or null, `decided` true for the group the decision settles; the platform records them (`notation_classes`), and `shared` returns each symbol's `classes` `[{label, entry: {id, symbol, status} | null, decided, meanings: [index], facts}]`, the most used first, and `unclassified`, the indexes of the wordings no sweep grouped. A symbol whose groups all point at an entry counts as settled. An answer without `classes` records none. A symbol read before sweeps grouped wordings is read once more. "same" also records the facts' word as a spelling of an entry that lists the same word as a clash (Towsner's "semigroup" for `semigroup (\beta\mathbb N)`, beside the algebraic "semigroup"). The same sweep types the agreed and local entries written with parameters nobody typed: `context.entries_to_type` lists `{id, symbol, status, meaning, params}` (the parameter names), and the answer's `types` gives `[{entry, params: [{name, type}]}]`; only the entry's own parameters are kept, never over types already given, and each entry is read once. A letter that is part of the name is typed `not a parameter`.

On a question: `strategy` adds up to 3 strategies with status `idea` and `subquestion` up to 5 open sub-questions, both stamped with the model; `derive` and `references` queue a `derive` or `bib` task on it with `text` as instructions; `check_answers` queues a review (a source check for a cited result) of each fact a proposed or ratified answer rests on. On a strategy: `derive`, `references`. On a file: `extract`. On a reference: `extract` (it needs a PDF), `references`. On a notation entry: `change` adds a proposed entry from the first item (`title` the symbol, `statement` its meaning), noting what it would replace (`NotationController::proposeChange`); `rewrite` and `settle` queue those sweeps. On a conversation: `extract`, refused when a project member is not a participant. Queued tasks are requested by the comment's author and count in their requests, with the checks of `POST /api/projects/{id}/ai/tasks` (`AiTaskController::queueFor`). The platform posts `reply` in the thread, followed by a line per action with what became of it, a refusal included ("Not started: …"). No action is fine: the reply alone.
  - A `derive` task has every fact with its `statement`, `proof`, `status`, `usable` (it may be built on), `deps` and `glossary`, as `GET /api/projects/{id}/proving-context` gives them, and `facts_note`. Toward a question, `question.answers` lists the answers proposed for it (`fact_id`, `answer`, `state`, `rationale`) with `answers_note`: a new fact that closes the gap of an almost answer is the most useful.
  - A `latex` task (needs the `latex` feature, for a client with LaTeX) is asked on a proved fact whose chain is checked; its context has `latex: {files: {"main.tex", "refs.bib"?}, sha256, title, facts}`. The client compiles it without shell escape and sends the PDF to `/api/ai/tasks/{id}/document`, then completes the task. A file made this way has `exported_fact` and is never extracted.
  - Reviews, Lean proofs and proof reviews give each fact its `definitions`: `[{symbol, meaning, from: "this fact" | "project notation"}]`, its own glossary and the agreed or local entries its rewrite uses. A review or Lean task with no dependency has `dependencies_note`. Each dependency has its `id`; in a Lean task, one with a compiled Lean proof also has `lean: {decl_name, code}`.
  - Proof reviews (`proof_review`, a sweep only, flagged `independent` in `GET /api/ai/procedures` and in its recipe): the proved facts no person and no AI of another company than their author checked at their current revision, six at a time (at most 50,000 characters), in the order of `Verification::rank`: what a proposed or ratified answer rests on first, then what results worth reading rest on, then the facts many others rely on, directly or not. A client sends, for an `independent` procedure, every model it could review with in `models.proof_review`, another company's first; the platform leases the task with the first one that has proofs to review, and the client runs it on that model's tool. A proof only its author's company checked waits for another company's model when one reviewed or asked for work in the project in the last 30 days; a sweep a model has nothing for goes back to waiting instead of ending. `context.facts` lists `{fact_id, label, title, kind, statement, proof, external_refs, sources, outside_refs, dependencies}`, where `sources` quotes the passages the fact was taken from (`{label, page, quote}`), so that the review can flag a statement whose base system or hypotheses differ from its source; the answer is `{summary, reviews: [{fact_id, verdict: "correct" | "gap" | "incorrect", explanation}]}`, recorded as AI reviews with the model. A proof is never put in the batch of a client running the model that wrote it: it waits for another model. A proof a model read and left out, unable to check it, goes to another model; after two models, it is left to people. An AI client's reviews are kept one per model (`fact_reviews` is unique per fact, revision, reviewer, kind and model): two models run under one member's key give two independent reviews, and a model's second review of a revision replaces its first. Off with `sweeps.review` false in `config.php`.
  - Source checks: when the cited results of a batch come from one reference with a PDF, `context.document` is that PDF as a document with one file, `{"id": "bib/{id}", "role": "pdf"}`, served by `GET /api/files/bib/{id}`. The verdict `unreadable` means the AI could not read the work at all; a check made without the source (`had_source` 0) that found nothing is made once more when the source can be read. A batch cut by its size limit counts as full: the next sweep of its kind starts at once. A new entry whose symbol differs from the facts' keeps their spelling as an `instance` variant, so that `semigroup` counts as `semigroup (\beta\mathbb N)`. A local entry created this way names `fact` as its definition, so it applies to that paper's facts.
  Members cannot ask for `rewrite_check` and `second_reading` (422): the platform queues them. Settings, in `config.php` under `sweeps`: `quiet_minutes`, `check_minutes`, `rewrite_hours`, `source_hours`, `check_hours`, `second_hours`, `symbols_hours`, `consolidate_hours` (0: only after extractions).
- `review` tasks receive `context.dependencies` with each one's `basis` and `status`, and `context.fact.outside_refs`. Clients from 1.13.0 review the proof relative to its dependencies, without web search.
- `consolidate` tasks need `"consolidate"` in `features`. The platform queues one when the last waiting extraction of a project ends, and a member can ask for one. They read `context.fact_texts` (every fact in short, with its source, `depends_on` and `topics`), `context.topics` and `context.earlier_suggestions`, and post proposals to `/api/projects/{id}/consolidation`. Each fact of `fact_texts` has its `basis` and its unresolved `outside_refs`. A `cite` proposal names in `ref` one of them: with `other_fact`, the fact that states its result; without, a new cited result with `title`, `statement` and `new_kind`. Accepting it creates that fact if needed, adds the dependency and resolves the reference. Every proposal carries a `confidence`: `high`, `medium` or `low`. When the project allows it (`consolidation_auto`, on by default; `POST /api/projects/{id}/consolidation/settings` `{"auto": bool}`, owners), a `high` proposal of kind `same`, `depends`, `kind`, `topics`, `cite`, `progress` or `notation` is applied at once, and a `medium` one of kind `topics` or `notation`, marked `auto_applied`; the answer to the post lists them in `applied`. One that cannot be applied, such as a cycle, waits for people. A `notation` proposal settles the project notation: `notation` `{action, entry, symbol, meaning, note, variants, params}` (`params` fills in the types of an entry that had none), with `action` `adopt` (the entry `entry`, still proposed, or a new entry from `symbol` and `meaning`; an entry of the same notion is used when there is one), `local` (an entry named in `entry`, or a new local entry from `symbol` and `meaning`, whose definition is `fact`; an agreed entry of the same notion is never made local this way) or `reject` (an entry named in `entry`); `fact` names a fact that defines or uses the symbol. `context.notation` lists the entries with `decided_by` (`null`, `consolidation` or `person`), and `context.local_notation` the symbols several facts define. An entry a person decided is never changed. Applying or undoing one queues the rewrite of the facts not written in the current notation; an entry decided this way has `auto_suggestion_id`, and `decided_by_kind` in `GET /api/projects/{id}/notation`. An `answer` proposal names an open question in `question` (an id from `context.open_questions`: `{id, parent_id, title, statement, status, answers}`) and `answer` (`positive` or `negative`), with the fact it rests on in `fact` and its caveats in `reason`; applied (at once when `high` or `medium`), it creates a proposed answer under the question by the AI, with its model, which a member ratifies or rejects, and undo withdraws it. Every other kind sends `question` and `answer` null. A consolidation is also queued when a `derive` task finishes with facts, and when a native prover round that added facts ends. A `progress` proposal marks a fact as real progress: applied, the fact gets `worth_reading` `{reason, at, model}` and appears in `reading` of `GET /api/projects/{id}/dashboard` for each member who has not opened, reviewed or dismissed it since (`POST /api/facts/{id}/reading/dismiss`). Applying a proposal records what it changed: `POST /api/fact-suggestions/{sid}/undo` (people; an owner for a merge or an open question a person accepted) reverts it, unmerging a merge, and sets its status to `undone`. An undone proposal is never made again. `GET /api/facts/{id}` lists the applied and undone changes of a fact in `history`. A merged fact keeps `merged_into`: `GET /api/facts/{id}` on it returns the fact it was merged into, with `merged_from`.
- A person can queue an `extract` task for a conversation. Clients that handle it send `"extract_conversation"` in `features`, read `context.conversation.messages`, and cite `{"type": "message", "id": …, "quote": …, "covers": …}`. The task reads only the messages and comments present at the request. The task carries `publish_private` when a participant approved sharing, and it fails instead of running if that part was edited, if the requester left, or if the conversation became private without approval.
- The official client sends `User-Agent: open-questions-client/X.Y.Z`. When that version is older than `min_version`, every request made with a personal key gets HTTP 426 with `{error, update_required: true, min_version, current_version}`, and the client must stop and ask its user to update. Other programs are not affected.
- A file or version uploaded by a person queues an `extract` task. `@AI` in a person's message or comment, including the first message of a conversation, queues an `ask` task, which a client that follows instructions takes as an `instruct` task when it is in a comment. Its `context.thread` ends at that message, with up to 100 messages. `GET /api/conversations/{id}` reports `ai_opinion` `{waiting, running, failed_task, clients}`. Text written by an AI never queues one.
- A task from a private conversation can be seen and claimed only by its participants.
- The answer to `@AI` is written by a system author, "AI assistant", with the model and responsible user of the client. It is not a project member and has no credential.
- `POST /api/ai/tasks/{id}/release` with `{"lease"}` gives a task back without counting an attempt, for a usage limit or a user stop.
- `oq.py` checks the user's limits before each claim, and offers the same engine through `oq.py app` (local interface) and `client/desktop` (Electron shell).
- By default (`ai_billing: subscription`), `oq.py` removes Anthropic and OpenAI API credentials from the AI process, and holds work if the tool is configured with a paid key. `oq.py limits --billing api` allows them.
- `POST /api/projects/{id}/ai/tasks` also accepts a personal key for `kind: derive` only, so that a client records the Danus run its user launched. `claim` accepts `task_id` to take that task.
- Danus starts only from the client's Run button or `oq.py danus run`, with stops on running time, session usage and weekly usage, and a choice to end or wait for the reset. A watchdog in the machine stops its workers if the client disappears.
- `oq.py danus setup --native --accept-risk` is an opt-in on macOS. It installs Danus in the client's own folder with Codex's sandbox on: agents can read the user's files, can write only in their folder and temporary folders, and have no direct network access.
- `oq.py danus setup --engine claude --accept-risk` (macOS, experimental) runs Danus unmodified through an adapter that replaces its `codex exec` command with `claude -p`: no shell, scoped file permissions, no API keys, the user's Claude settings ignored. Claude reports no usage percentage, so a run needs a time limit and also stops at daily caps and reported limits.
- `oq.py danus setup` installs Danus at a pinned commit in an isolated machine: Lima on macOS, WSL on Windows, Docker or Podman on Linux. No folder of the computer and no platform key enter it.
- `oq.py` runs the AI read-only, without the platform key, and checks and submits its structured answer. A quotation that is not in the file is refused when the text of the file is available.

### Importing from Danus
With `"format": "danus"`, items use the Danus fields `fact_id`, `predecessors`, `statement`, `proof`, `intuition`, `glossary_introduces`, `external_refs`.
Items may carry `labels` (default `conclusion`), and the importer reads them from the Danus memory. They are stored as `deduced` with `tool: "danus"`, and `fact_id` makes the import idempotent. They arrive as **unchecked**, because the platform cannot confirm a Danus verifier run,
and that verifier is itself an LLM.

```bash
python3 client/oq.py danus push path/to/project/fact_graph --project 1 --model MODEL_USED_BY_DANUS --dry-run
```

`danus watch` sends new facts as they appear. `danus pull` copies platform facts to a separate `platform_facts` folder and never changes the graph. `danus serve --command "…"` claims `derive` tasks and runs your command, with `{task}` and `{graph}` replaced by paths. Danus runs with full shell access, so use `serve` only on an isolated machine.

## Audit API

An owner creates an **audit key** on the project's Admin page, under **Audit access**. It starts with `oqa_`, is shown once, lasts 1, 7 or 30 days, and can be revoked. It reads one project and nothing else: it signs nobody in, so every other route answers `401`. Sources from private conversations stay hidden as for a member outside them, and no email or ORCID iD is included. Each use is counted on the Admin page.

| Method | Path | Returns |
|---|---|---|
| GET | `/api/audit/project` | The project, its summary and these routes. |
| GET | `/api/audit/graph` | Every fact, briefly, and the dependencies `[fact, depends_on]`. |
| GET | `/api/audit/facts?offset=0` | 200 full facts at a time, as `GET /api/facts/{id}` gives them: statement, proof, sources, reviews, other proofs, Lean proofs, rewrites. `next` is the next offset, or null. |
| GET | `/api/audit/notation` | The notation entries (each with `decided_by`: `null`, `consolidation` or `person`, and `decided_at`), the symbols several facts define (a symbol written `$FS(H)$` in a fact is the same as `FS(H)`), and the rewriting progress. |

Owners manage keys with `GET`/`POST /api/projects/{id}/audit-keys` (`{"label", "days"}`) and `DELETE /api/projects/{id}/audit-keys/{kid}`. To save everything for a local audit, from a copy of the repository:

```bash
OQ_AUDIT_URL=https://projects.example.org OQ_AUDIT_KEY=oqa_… npm run audit:fetch
```

It writes `audit/` (git-ignored): `project.json`, `graph.json`, `notation.json`, `facts.json`, and one readable `facts/*.md` per fact. The key is sent only over https, and never printed.

## Model of AI-generated content

Everything an agent or AI client writes stores the model that produced it: messages, comments, files and their versions, bibliography entries,
facts, reviews, Lean proofs and Lean checks. Send `ai_model` with a write to record the exact model. An agent falls back on its default model.
A personal key has no default, so `ai_model` is required. Without a model, the write is refused with a 422.

Each AI item also records:

- **The user it corresponds to** (`ai_user_id`, `ai_user_name`): the owner of the personal key, or the project owner who issued the agent's token. The server sets it, so a client cannot claim another user.
- **The generation time** (`ai_generation_ms`), when the client sends `generation_seconds` with the write. It is optional and must be a real measurement, not an estimate. In a batch, send it per fact, because a time for the whole batch does not describe one fact.

## What is new

`GET /api/counters?project=ID` returns the unread state of the caller: `totals` per type and `unread[type][id]` per item, for `conversation`, `fact`, `document`, `bib`, `question` and `member`.
Reading through a personal key never marks anything as read. What a user's AI client writes stays unread for that user until they open it.

## Ready-made agent

[`examples/claude_agent.py`](../examples/claude_agent.py) is a small agent built on Claude (Anthropic API).
It polls for notifications. When it is @mentioned or added to a conversation, or someone replies to its comment,
it reads the discussion and the PDFs of the @mentioned files, then answers in the same place.

```bash
pip install anthropic requests
export OQ_URL=https://research.example.org OQ_TOKEN=oq_… ANTHROPIC_API_KEY=sk-ant-…
python examples/claude_agent.py --dry-run   # show what it would do, no API calls
python examples/claude_agent.py             # run (polls every minute)
```

You can run it anywhere, for example on your laptop or a small server with cron and `--once`. OVH shared hosting does not run
long-lived processes.
